```md
经过对 Hi3556V200 SDK 代码、内核源码、底板原理图（A-PCB-MB-SMART.pdf）以及 smart-640-v2 应用层源码的完整排查，以下为您梳理将红外 Sensor（FPGA）从 BT656 修改为 DVP（外同步 Digital Camera / DC 模式）的完整修改点与技术细节：

1. 核心架构认知澄清（海思平台与瑞芯微 Rockchip 的本质差异）
  - 瑞芯微平台：视频输入接口（CIF / DVP / MIPI）严格走 Linux 标准 V4L2 子系统与设备树（DTS），通过 endpoint 的 bus-type（4 为 DVP，5 为 BT656）、hsync-active、vsync-active、pclk-sample 等属性以及驱动 probe 进行配置。
  - 海思平台（Hi3556V200）：完全不通过 Linux 内核设备树配置 VI。
    - 在 hi3556v200-demb.dts 和 hi3556v200.dtsi 中，没有任何 VI / 视频捕获接口的相关节点（设备树仅管理内存基址、I2C、SPI、按键、ADC等基础外设）。
    - 海思的所有视频输入接口均由其专有 MPP 架构（hi3559v200_vi.ko、hi_mipi_rx.ko、sys_config.ko）在系统启动加载阶段，以及应用层调用 MPI API（HI_MPI_VI_*、/dev/hi_mipi ioctl）来进行动态配置。
    - 因此，您不需要修改 DTS 文件。

2. 原理图极其关键的硬件排查发现（A-PCB-MB-SMART.pdf 存在 HS/VS 交叉互换）
  - 对照原理图第 7 页（FPGA 端）与第 5 页（Hi3556V200 端），时钟与数据线是一一对应的：
    - 时钟：FPGA_CLK -> R103 (22Ω) -> FPGA_SOC_CLK -> SoC 球号 Y16 (VI_CLK)
    - 数据：FPGA_D0~D7 -> R82~R93 (22Ω) -> FPGA_SOC_D0~D7 -> SoC 球号 W19, Y20, Y19, W18, Y18, V17, W17, W16 (VI_DATA0~VI_DATA7)
  - 但是，外同步信号（HSYNC 和 VSYNC）在原理图上存在交叉反接：
    - 原理图 Page 7（FPGA 端）：
      Pin H9 标为 FPGA_HS，经 R95 连接到网络 FPGA_SOC_VS；
      Pin H8 标为 FPGA_VS，经 R96 连接到网络 FPGA_SOC_HS。
    - 原理图 Page 5（SoC 端）：
      网络 FPGA_SOC_HS 接到了 SoC 的球号 U17（VI_HS）；
      网络 FPGA_SOC_VS 接到了 SoC 的球号 V18（VI_VS）。
    - 硬件连接结果：
      FPGA 的 Pin H9 最终连到了海思的 VI_VS（场同步）！
      FPGA 的 Pin H8 最终连到了海思的 VI_HS（行同步）！
    - 对策建议：
      在 FPGA 的引脚约束（XDC / LPF）中，务必将 HSYNC 分配给 Pin H8，VSYNC 分配给 Pin H9（即在 FPGA 端对调），或者在 Verilog 输出逻辑中颠倒两者；否则海思硬件单元会收到错误的行场时序而无法锁帧。

3. 引脚复用修改（Pinmux / IOCFG 寄存器层）
  - 物理基地址：IOCFG 基地址为 0x114F0000。
  - BT656 与 DVP 的区别：
    - BT656 使用数据流内嵌 SAV/EAV，不使用外同步脚，因此海思默认只把 VI_CLK 和 VI_DATA0~7 设为 VI 功能，外同步脚通常配置为普通 GPIO 或未配置。
    - DVP（外同步）必须将 VI_HS 和 VI_VS 引脚复用为 VI 功能（功能 1，写入 0x471）。
  - 对应寄存器：
    - 0x114F0060：VI_VS（球号 V18），需写入 0x471
    - 0x114F0064：VI_HS（球号 U17），需写入 0x471
    - 0x114F0068：VI_CLK（球号 Y16），写入 0x461
    - 0x114F0040 ~ 0x114F005C：VI_DATA0 ~ VI_DATA7，写入 0x471
  - 代码位置与生效机制：
    - SDK 源码位置：_Workspace_/Hi3559V200_SDK_V2.0.1.0/interdrv/sysconfig/sys_config.c
    - 在 sys_config.c 中，vi_dc_mode_mux() 函数负责上述寄存器配置：
      sys_writel(g_reg_iocfg_base + 0x0060, 0x471);
      sys_writel(g_reg_iocfg_base + 0x0064, 0x471);
    - 该函数由内核模块参数 g_cmos_yuv_flag 控制。当 g_cmos_yuv_flag == 3 时，会自动触发 vi_dc_mode_mux()。

4. 驱动与加载脚本修改（smartload / run_app.sh）
  - 脚本文件位置：
    - 工具链打包路径：smart/tools/package/app/extko/smartload
    - 板端运行路径：/root/extko/smartload
  - 修改变量参数：
    - SNS_TYPE0=dc;
    - YUV_TYPE0=3; （0 为 raw，1 为 bt1120，2 为 bt656，3 为 dc）
    - 确保加载 sys_config.ko 时传入：
      insmod sys_config.ko chip=$CHIP_TYPE sensors=sns0=$SNS_TYPE0,sns1=$SNS_TYPE1, g_cmos_yuv_flag=$YUV_TYPE0
    - 注：若板端运行时是通过 himm 手动配置，也可以在启动脚本中直接运行：
      himm 0x114f0060 0x471
      himm 0x114f0064 0x471

5. 应用层代码修改（smart-640-v2 对应的 media_vi.c）
  - 源码位置：_Workspace_/smart/app/mickey_smart/modules/media/src/media_vi.c
  - 修改环节一：MIPI / Combo 设备属性（vi_mipi_init 函数）
    - 打开 /dev/hi_mipi 并通过 HI_MIPI_SET_DEV_ATTR 设置属性：
      dev_attr.input_mode = INPUT_MODE_CMOS; （若之前是 BT656 则为 INPUT_MODE_BT656）
      dev_attr.img_rect.width = 640;
      dev_attr.img_rect.height = 512;
      dev_attr.mipi_attr.input_data_type = DATA_TYPE_YUV422_8BIT;
      for (int i = 0; i < MIPI_LANE_NUM; i++) {
          dev_attr.mipi_attr.lane_id[i] = -1;
      }
  - 修改环节二：海思 VI 设备属性（vi_dev_ch_init 函数中的 HI_MPI_VI_SetDevAttr）
    - 接口模式修改：
      dev_attr.enIntfMode = VI_MODE_DIGITAL_CAMERA; （BT656 为 VI_MODE_BT656）
    - 掩码与序列：
      dev_attr.au32ComponentMask[0] = 0xFF0000;
      dev_attr.enDataSeq = VI_DATA_SEQ_UYVY; （需与 FPGA 发送顺序对齐，如 UYVY 或 YUYV）
      dev_attr.enInputDataType = VI_DATA_TYPE_YUV;
      dev_attr.enScanMode = VI_SCAN_PROGRESSIVE;
    - 外同步关键参数配置（dev_attr.stSynCfg，DVP 模式必须配置，BT656 模式下无效）：
      dev_attr.stSynCfg.enVsync = VI_VSYNC_FIELD;        // 场同步信号类型：VI_VSYNC_FIELD（电平/场模式）或 VI_VSYNC_PULSE（脉冲模式）
      dev_attr.stSynCfg.enVsyncNeg = VI_VSYNC_NEG_HIGH;  // 场同步极性：VI_VSYNC_NEG_HIGH（高有效/正脉冲）或 VI_VSYNC_NEG_LOW（低有效）
      dev_attr.stSynCfg.enHsync = VI_HSYNC_VALID_SINGNAL;// 行同步信号类型：VI_HSYNC_VALID_SINGNAL（有效信号/DE模式）或 VI_HSYNC_PULSE（行脉冲）
      dev_attr.stSynCfg.enHsyncNeg = VI_HSYNC_NEG_HIGH;  // 行同步极性：VI_HSYNC_NEG_HIGH（高有效）或 VI_HSYNC_NEG_LOW
      dev_attr.stSynCfg.enVsyncValid = VI_VSYNC_VALID_SINGAL;
      dev_attr.stSynCfg.enVsyncValidNeg = VI_VSYNC_VALID_NEG_HIGH;
    - 消隐与有效宽度参数（stTimingBlank）：
      在 sample_vio_config.c 的官方参考实现中：
      dev_attr.stSynCfg.stTimingBlank.u32HsyncHfb = 0;
      dev_attr.stSynCfg.stTimingBlank.u32HsyncAct = 640;
      dev_attr.stSynCfg.stTimingBlank.u32HsyncHbb = 0;
      dev_attr.stSynCfg.stTimingBlank.u32VsyncVfb = 0;
      dev_attr.stSynCfg.stTimingBlank.u32VsyncVact = 512;
      dev_attr.stSynCfg.stTimingBlank.u32VsyncVbb = 0;
      （注意：若 FPGA 的 HSYNC 是数据有效 DE 信号，且只在 640 个有效点拉高，HsyncAct 填 640；如果当前代码中设为 0 且出现报错，请设为 640 和 512）。

6. 配置文件确认（config_mediamode.ini）
  - 文件位置：smart/app/mickey_smart/resource/smart-640-v2/cfg/config_mediamode.ini
  - 确认 [vcap.1] 的配置：
    [vcap.1]
    enable = "1"
    sns_obj = "MK2-640-512"
  - 该名称与 media_vi.c 中的 strcmp(..., "MK2-640-512") 对应，命中后进入 640*512 分辨率分支。

7. 板端联调与排查命令建议
  - 在板端使用 himm 检查引脚复用是否正确生效：
    himm 0x114f0060  # 查看是否为 0x471 (VI_VS)
    himm 0x114f0064  # 查看是否为 0x471 (VI_HS)
  - 查看海思 VI 模块运行状态与错误计数：
    cat /proc/umap/vi
    - 检查 IntCnt（中断计数）是否在持续递增。若完全不增，说明没有收到有效的 PCLK 或 VSYNC/HSYNC 中断。
    - 检查 Width/Height 是否正确锁定为 640x512。
    - 检查 ErrCnt、LostCnt 是否有异常增长。
  - 使用示波器抓取 FPGA 侧 Pin H8、Pin H9 和 PCLK，核对信号电平有效极性是否与 stSynCfg.enVsyncNeg / enHsyncNeg 配置一致。
```

### 2

```md
硬件与 FPGA 同事能够直接在 FPGA 侧通过修改 XDC 约束来对冲底板 PCB 的引脚反接，是非常高效且低成本的方案。

针对您的诉求，我已为您系统性排查了后续可能面临的潜在风险，并制定了完整的迁移实施方案，详细技术文档已输出至 .playground/hi3556v200_bt656_to_dvp_plan.md。

以下为您梳理核心风险点与方案要点：

1. 必须重点关注的 5 大潜在风险与规避策略

  - 风险一：PCLK 时钟采样边沿与建立/保持时间（Setup/Hold Time）
    - 风险表现：BT.656 自带 SAV/EAV 对齐机制，对时钟相位的容忍度相对较高；切换为 DVP 后，海思每个时钟周期都直接依边沿采样数据。若 FPGA 在 PCLK 上升沿更新数据，海思 VI 也在上升沿采样，走线延迟会导致采样点正好落在数据边沿抖动区，造成画面出现随机雪花噪点、跳变横线或偶发丢行。
    - 规避对策：建议 FPGA 侧输出 PCLK 时做 180 度相位反转（或在下降沿更新数据、上升沿给出时钟），确保到达海思引脚时，PCLK 上升沿正好位于数据有效窗口（眼睛图）的正中心。

  - 风险二：行同步信号协议模式匹配（DE 有效模式 vs 行脉冲模式）
    - 风险表现：DVP 接口的 HSYNC 有两种主流形态：第一种是 DE（Data Enable）模式，仅在每行 640 像素传输期间为高电平；第二种是行同步脉冲模式，在行起始发脉冲，之后跟随前肩、有效区和后肩。若 FPGA 输出的是 DE 信号，但海思按行脉冲解析，VI 控制器将无法识别有效数据窗口，导致画面黑屏或严重撕裂。
    - 规避对策：建议 FPGA 侧采用标准的 DE 模式（数据有效时拉高）。海思应用层配置 dev_attr.stSynCfg.enHsync = VI_HSYNC_VALID_SINGNAL，二者必须严格约定并匹配。

  - 风险三：场同步信号极性与类型定义（Pulse vs Field）
    - 风险表现：VSYNC 存在正负脉冲（Pulse）与高低电平场（Field）区别。若极性定义相反，海思会将消隐区误判为图像区，导致画面整体垂直错位、滚屏或截断。
    - 规避对策：与 FPGA 明确 VSYNC 是正脉冲（Pulse）还是电平场信号。海思端在 dev_attr.stSynCfg.enVsync 与 enVsyncNeg 中配置相同极性。

  - 风险四：YUV422 数据字节序列对齐（颜色失真风险）
    - 风险表现：8-bit 传输 640x512 的 YUV422 时，每个像素占用 2 个字节。若 FPGA 吐出的顺序是 Y0, U0, Y1, V0（YUYV），而海思软件配置为 U0, Y0, V0, Y1（UYVY），会导致亮度 Y 和色度 U/V 错位，画面会出现严重的伪彩、偏紫或偏绿。
    - 规避对策：明确 FPGA 发送端的数据序列。若 FPGA 输出 YUYV，将 media_vi.c 中的 dev_attr.enDataSeq 改为 VI_DATA_SEQ_YUYV；若输出 UYVY，则维持 VI_DATA_SEQ_UYVY。

  - 风险五：消隐结构体（stTimingBlank）有效宽高赋值
    - 风险表现：原 smart-640-v2 代码中 u32HsyncAct 和 u32VsyncVact 被置为 0。但在海思官方 DVP 标准实现（sample_vio_config.c）中，要求将其明确填入物理分辨率（640 与 512）。部分 SDK 底层在 Act 填 0 时会报错或丢弃缓冲。
    - 规避对策：在 media_vi.c 中，显式将 dev_attr.stSynCfg.stTimingBlank.u32HsyncAct 赋值为 640，u32VsyncVact 赋值为 512。

  - 风险六：开机门控等待流就绪（PTS 连续性）超时风险
    - 风险表现：之前在 media_vi.c 中增加了 media_vi_wait_stream_ready() 函数用于 Logo 平滑过渡。若 FPGA 上电自检或输出稳定时钟滞后于海思启动，VI 将长时间拿不到中断，导致开机阶段判定超时。
    - 规避对策：确保 FPGA 在海思加载 MPP 模块前已完成上电自检并持续输出稳定的 PCLK 与同步信号。

2. 具体改造实施方案纲要

  - 步骤一：FPGA 侧 XDC 引脚约束修改
    - HSYNC 引脚映射到芯片封装引脚 H8（对应原理图网络 FPGA_SOC_HS -> 海思 VI_HS 球号 U17）。
    - VSYNC 引脚映射到芯片封装引脚 H9（对应原理图网络 FPGA_SOC_VS -> 海思 VI_VS 球号 V18）。
    - PCLK（引脚 H7）与 DATA0~7 约束保持不变，IO 电平标准维持 LVCMOS18（1.8V）。

  - 步骤二：驱动加载脚本参数调整（smartload）
    - 文件位置：smart/tools/package/app/extko/smartload（板端对应 /root/extko/smartload）。
    - 将变量设置确认为：
      SNS_TYPE0=dc
      YUV_TYPE0=3
    - 说明：当 YUV_TYPE0=3 传给 sys_config.ko 时，驱动会自动触发 vi_dc_mode_mux()，将 0x114F0060（VI_VS）和 0x114F0064（VI_HS）复用寄存器配置为 0x471。

  - 步骤三：应用层媒体代码调整（smart-640-v2: media_vi.c）
    - 文件位置：smart/app/mickey_smart/modules/media/src/media_vi.c。
    - 在 vi_mipi_init() 中，确认 dev_attr.input_mode = INPUT_MODE_CMOS。
    - 在 vi_dev_ch_init() 中，确认接口模式为 dev_attr.enIntfMode = VI_MODE_DIGITAL_CAMERA。
    - 修正 stTimingBlank 参数：
      dev_attr.stSynCfg.stTimingBlank.u32HsyncAct = 640;
      dev_attr.stSynCfg.stTimingBlank.u32VsyncVact = 512;
    - 根据与 FPGA 约定的极性和数据序列，核对 enDataSeq（UYVY/YUYV）和 stSynCfg（enHsync / enVsync）。

  - 步骤四：配置文件核对（config_mediamode.ini）
    - 文件位置：smart/app/mickey_smart/resource/smart-640-v2/cfg/config_mediamode.ini。
    - 确认 [vcap.1] 的 sns_obj = "MK2-640-512"，确保进入 640*512 对应的逻辑分支。

3. 板端上电验证手段

  - 寄存器复用校验：
    - himm 0x114f0060  # 查看是否为 0x00000471（VI_VS）
    - himm 0x114f0064  # 查看是否为 0x00000471（VI_HS）
  - 中断与分辨率状态监控：
    - cat /proc/umap/vi
    - 重点检查 IntCnt 是否以 50Hz 匀速增加；
    - 检查 Width/Height 是否稳定锁定在 640x512；
    - 检查 LostFrame 和 CCnt 是否保持为 0。

4. 交付文档说明

  - 方案完整文档已输出到：.playground/hi3556v200_bt656_to_dvp_plan.md
  - 文档内包含了完整的背景分析、风险矩阵、寄存器配置说明、代码段修改对比以及调试排错速查手册，您可以随时在 .playground 目录下直接 review 或取用。
```
